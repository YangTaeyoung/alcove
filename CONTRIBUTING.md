# Contributing to Alcove

Alcove is in early development. It is five layers stacked on each other, and a
change in one usually means a change in another:

| Layer | Where | Language |
|---|---|---|
| Engine | `qemu-patches/` applied to QEMU `v11.1.1` by `scripts/build-qemu.sh` | C, meson |
| Libraries | `AlcoveKit/` — `AlcoveDisplayProtocol`, `AlcoveQMP`, `AlcoveEngine`, `AlcoveAgent`, `AlcoveControl`, `alcovectl` | Swift 6 |
| App | `Alcove/` — SwiftUI + AppKit + Metal, project generated by XcodeGen from `project.yml` | Swift 6 |
| Guest tools | `guest-tools/` — the `alcove-agent` that runs inside Windows and Linux guests | Go |
| Automation | `mcp/` — MCP server over the control socket | TypeScript |

The wire formats between them are specified in `docs/display-protocol.md`,
`docs/agent-protocol.md` and `docs/control-protocol.md`. Change a format and
you change the document in the same commit.

CI (`.github/workflows/ci.yml`) runs on every push to `main` and every pull
request, and covers only what needs no VM: the Swift package (`swift build
--build-tests` and `swift test`), the Go guest tools (`go vet` and `go test`
plus the Windows and Linux ARM64 cross-builds), and the MCP server (`npm ci &&
npm run build`, then `mcp-smoke.py --list-only`). It never builds the QEMU
engine, so the engine build, `display-backend.py`, the real-engine
`VMControllerTests`, the `xcodegen`/`xcodebuild` app build and every guest
suite are covered by the checklists below and by nothing else. Run them
locally before opening a PR.

## Getting a working tree

You need an Apple silicon Mac. The engine is a real QEMU build, so the
prerequisites are real too (this is the `## Requirements` section of the
README, restated as commands):

```sh
xcode-select -p                       # Xcode 26; macOS 15 or later (developed on macOS 26)
brew install meson pkgconf ninja glib pixman dtc libslirp capstone libusb zstd libpng swtpm xcodegen go
```

- `libpng` is not optional: `build-qemu.sh` passes `--enable-png`, and QMP
  `screendump` defaults to PNG, which is what `AlcoveQMP` and
  `scripts/test/install-windows.py` use.
- `swtpm` backs the vTPM a Windows 11 guest needs; `xcodegen` generates
  `Alcove.xcodeproj`; `go` builds the guest agent.
- QEMU's `configure` needs Python 3.11+ (`tomllib`). The macOS system
  `python3` is 3.9 and cannot run it, so `build-qemu.sh` defaults `PYTHON` to
  `$(brew --prefix)/bin/python3` — Homebrew's `python3` arrives as a `meson`
  dependency. Override with `PYTHON=`.
- **Clone somewhere short.** Unix socket paths are capped at 104 bytes on
  macOS. The test scripts create sockets under `build/test-*/` and `$TMPDIR`,
  so a deep checkout path breaks them. (The app itself is safe: it hashes the
  bundle path into `/tmp/alcove-<uid>/<hash>/`.)
- Windows guest work additionally needs a Windows 11 ARM64 ISO and
  `virtio-win.iso` in `images/` — see the README's image table and
  `scripts/fetch-windows-iso.sh`.

`build/`, `images/`, `Alcove.xcodeproj/`, `AlcoveKit/.build*/`, `mcp/dist/`
and `mcp/node_modules/` are git-ignored. `Alcove.xcodeproj` is generated:
never commit it, and never edit it by hand — edit `project.yml` and re-run
`xcodegen generate`.

## Build the engine first

```sh
scripts/build-qemu.sh          # -> build/qemu-build/qemu-system-aarch64
```

Nothing else works until this succeeds. Alcove's display path *is* a QEMU
patch: `EngineLocator.locate()` rejects a stock QEMU precisely because it has
no `alcove` display backend
(`AlcoveKit/Sources/AlcoveEngine/EngineLocator.swift`), so a Homebrew
`qemu-system-aarch64` on `$PATH` will not do. The real-engine tests in
`AlcoveKit/Tests/AlcoveEngineTests/VMControllerTests.swift` skip themselves
with `engine not built; run scripts/build-qemu.sh` when it is missing, and
`scripts/test/all.sh` runs the build as its first step.

What the script does, in order:

1. Shallow-clones `https://gitlab.com/qemu-project/qemu.git` at `QEMU_TAG`
   (default `v11.1.1`) into `build/qemu-src` if it is not there yet.
2. Checks that every Homebrew package it needs is installed and fails with the
   `brew install` line if one is not.
3. Makes `build/qemu-src` exactly *tag + `qemu-patches/*.patch`* (see below).
4. Configures into `build/qemu-build` — `--target-list=aarch64-softmmu`,
   `--enable-hvf --enable-cocoa --enable-slirp --enable-libusb --enable-tpm`,
   `--enable-png`, `--disable-pvg` (no apple-gfx devices) and
   `-Dalcove=enabled` — then `ninja`.
5. Prints the version and **verifies the `com.apple.security.hypervisor`
   entitlement** on the binary, exiting non-zero if it is missing. QEMU's own
   install step ad-hoc-signs the binary with it; a copy or re-sign that loses
   it cannot open Hypervisor.framework at all — `hv_vm_create()` returns
   `HV_DENIED` and QEMU exits with *"Could not access HVF. Is the executable
   signed with com.apple.security.hypervisor entitlement?"*
   (`docs/research/qemu-11.1.1-virt-machine-devices.md`).

`-Dalcove=enabled` is passed as a raw meson option on purpose: QEMU's
`configure` rejects unknown `--enable-*` flags, and the alternative is
carrying a regenerated `scripts/meson-buildoptions.sh` hunk in the patch
series (`docs/research/qemu-11.1.1-build-and-patching.md`, section 2.3).

Useful knobs: `--clean` (drop `build/qemu-build` and re-configure),
`--install` (also `ninja install` into `build/qemu-install`), and the
environment variables `QEMU_TAG`, `QEMU_GIT`, `PYTHON`, `JOBS`
(default: CPU count minus two) and `ALCOVE_CONFIGURE_EXTRA`.

The first build is a full QEMU build and takes a while. Re-runs are cheap:
when the tree is already at the tag with the patches applied the script prints
`source tree already at v11.1.1 + patches; leaving it untouched` and `ninja`
has nothing to do.

At runtime the engine is found through `$ALCOVE_QEMU_DIR`, then the app
bundle's `Resources/qemu`, then the development tree `build/qemu-build`, then
`$PATH` and Homebrew.

## Running the tests

`scripts/test/all.sh` is the full local verification. It runs, in this order,
and stops at the first failure:

1. `scripts/build-qemu.sh` — the engine (a no-op when already patched and built).
2. `python3 scripts/test/display-backend.py` — boots `qemu-system-aarch64`
   under HVF with EDK2 firmware only (no OS), speaks the Alcove display
   protocol over a unix socket, maps the shared framebuffer and asserts:
   `hello`/`switch`/`update` arrive with a non-blank frame, injected keys
   change the screen at the UEFI shell, pointer messages are accepted, and
   QEMU says `bye` and cleans up its shared files on `SIGTERM`.
3. `python3 scripts/test/install-windows.py --selftest` — the offline helper
   checks of the Windows install harness; no QEMU, no ISO.
4. `(cd AlcoveKit && swift build --product alcovectl && swift test)` — the
   Swift package: display protocol, QMP, engine, agent and control tests. The
   `VMControllerTests` boot the real engine; the same state machine is also
   covered without QEMU in `VMControllerFakeEngineTests`.
5. `(cd guest-tools && go vet ./... && go test ./...)` plus cross-builds of
   the agent to `build/alcove-agent-windows-arm64.exe`
   (`-ldflags "-H windowsgui"`, so it has no console window) and
   `build/alcove-agent-linux-arm64`.
6. `xcodegen generate` and `xcodebuild -project Alcove.xcodeproj -scheme Alcove
   -configuration Debug -derivedDataPath build/DerivedData build`.

The suites `all.sh` deliberately leaves out, because they need disk images or
an installed guest:

| Command | Needs |
|---|---|
| `scripts/test/boot-ubuntu.sh` | `images/noble-server-cloudimg-arm64.img`; boots it headless and waits for the serial login prompt |
| `python3 scripts/test/install-windows.py --fresh` | the Windows 11 ARM64 ISO and `virtio-win.iso`; unattended install. Without `--fresh` it boots and re-checks the installed disk |
| `python3 scripts/test/agent-windows.py` | the `Windows 11` bundle with forwards `2222->22` and `7646->7645`, the harness SSH key, and `build/alcove-agent-windows-arm64.exe` |
| `python3 scripts/test/agent-linux.py` | the Ubuntu bundle with forwards `2223->22` and `7647->7645`, and `build/alcove-agent-linux-arm64` |
| `python3 scripts/test/mcp-smoke.py --list-only` | `mcp/dist/` — run `cd mcp && npm install && npm run build` first. `--vm "Windows 11"` drives a real guest end to end |
| `python3 scripts/test/ctl.py <op> key=value …` | not a test — a one-shot client for the control socket, handy while debugging |

## Working on the QEMU patch series

`qemu-patches/0001-ui-add-alcove-display-backend.patch` is a plain
`git diff` (not `git format-patch`) against the pinned tag. It touches six
files: `meson.build`, `meson_options.txt`, `qapi/ui.json`, `qemu-options.hx`,
`ui/meson.build`, and the new `ui/alcove.c`.

`qemu-patches/0002-hw-nvme-reset-the-controller-before-loading-its-state.patch`
touches `hw/nvme/ctrl.c`: the NVMe controller frees its queues and clears its
AER request pointers before its state is loaded, so `snapshot-load` works on a
machine whose guest has used the controller.

`qemu-patches/0003-accel-hvf-log-dirty-pages-of-writable-ram-only.patch`
touches `accel/hvf/hvf-all.c`: starting, clearing and stopping dirty logging
(`snapshot-save`, `migrate`) changes the HVF protection of writable RAM only.
The flash that holds the UEFI variables is a ROM device: it has no HVF mapping
while the guest programs it and a read-only one otherwise, and it keeps both
through a snapshot.

With more than one patch in the series, export each with a pathspec, e.g.
`git -C build/qemu-src diff --cached HEAD -- hw/nvme/ctrl.c` for the NVMe
patch, `-- accel/hvf/hvf-all.c` for the HVF one and
`-- . ':(exclude)hw/nvme/ctrl.c' ':(exclude)accel/hvf/hvf-all.c'` for the
display backend.

`build-qemu.sh` applies the series with `git apply --index`, so after a build
the patched files are **staged** in `build/qemu-src`. The loop is:

```sh
scripts/build-qemu.sh                       # tree at v11.1.1 + patches
$EDITOR build/qemu-src/ui/alcove.c          # hack
ninja -C build/qemu-build                   # rebuild only

# export before anything resets the tree:
git -C build/qemu-src add -A
git -C build/qemu-src diff --cached HEAD > qemu-patches/0001-ui-add-alcove-display-backend.patch

scripts/build-qemu.sh                       # must print "leaving it untouched"
```

`add -A` matters: a new file is invisible to `git diff HEAD`, and the staged
tree is exactly what `build-qemu.sh` compares against when it decides whether
the tree already equals *tag + patches*. If that final run re-applies the
patches instead of leaving the tree alone, your exported patch and your tree
disagree — fix the patch, not the tree.

The script does have a safety net: before resetting a tree that is neither
pristine nor exactly the patch series, it writes
`build/qemu-src-discarded-<timestamp>.diff` and prints where. Treat that as a
recovery mechanism you never wanted to use, not as a workflow.

Two more rules for engine work:

- Splitting the series is fine — the script applies `qemu-patches/*.patch` in
  shell glob order, so keep the `NNNN-` prefixes ordered and unique.
- `AlcoveKit/Sources/AlcoveDisplayProtocol/QKeyCode.swift` is generated from
  the patched tree and must never be hand-edited. Regenerate it whenever
  `qapi/ui.json` or `QEMU_TAG` changes:
  `scripts/gen-qkeycode.py build/qemu-src/qapi/ui.json > AlcoveKit/Sources/AlcoveDisplayProtocol/QKeyCode.swift`
- A change to the socket messages in `ui/alcove.c` is a change to
  `docs/display-protocol.md` and to `AlcoveDisplayProtocol`. All three move
  together.

Engine code is a derived work of QEMU: `ui/alcove.c` carries
`SPDX-License-Identifier: GPL-2.0-or-later`, and any new file you add to the
series needs the same header. The rest of the tree runs as a separate process
from QEMU and is licensed separately — check the repository's licensing files
before copying code in either direction.

## Conventions

These are what the tree already does; match them rather than your editor's
defaults. `.editorconfig` covers indentation.

**Swift** (`AlcoveKit/`, `Alcove/`)

- Swift 6 language mode, strictly. The package sets
  `swiftLanguageModes: [.v6]`; the app target sets
  `SWIFT_STRICT_CONCURRENCY: complete`. Stateful clients are actors
  (`QMPClient`, `AgentClient`); everything crossing a boundary is `Sendable`.
  `@unchecked Sendable` is used only where the invariant is spelled out on the
  type itself (`ControlServer`) — do not add one silently.
- **No third-party Swift dependencies.** `AlcoveKit/Package.swift` declares no
  package dependencies at all, and the app links only AlcoveKit products plus
  `Metal`/`MetalKit`. Foundation, Dispatch, CryptoKit, AppKit, SwiftUI and
  Metal are the budget. A PR that adds a package dependency needs to argue for
  it first, in an issue.
- Doc comments (`///`) on public API, and make them earn their place: say why
  and under what constraint, not what the signature already says.
  `VMBundle.socketDirectory` explaining the 104-byte socket limit, and
  `loadConfig()` explaining why a migrated config is written back at once, are
  the house style.
- Four spaces, no tabs.
- Tests live next to the feature: `AlcoveKit/Tests/<Target>Tests/` mirrors
  `AlcoveKit/Sources/<Target>/`, and every library target has a test target.
  Prefer a fake over a real guest (`FakeQMPServer`,
  `VMControllerFakeEngineTests`), then add the real-engine test that only the
  real engine can prove — and make it `XCTSkip` when the engine is absent.

**Go** (`guest-tools/`)

- `gofmt` (tabs), `go vet ./...` clean.
- Standard library only: `go.mod` has no `require` block, and the agent has to
  drop into a fresh guest as a single static binary.
- Platform code splits by build tag into `*_windows.go` / `*_other.go` /
  `*_linux.go` files, not by `runtime.GOOS` branches inside one function.

**TypeScript** (`mcp/`) — two spaces, ESM (`"type": "module"`), `npm run build`
(`tsc`) must be clean.

**Python** (`scripts/`) — four spaces, standard library only, a module
docstring that states the usage line, and a non-zero exit on failure.

**Shell** (`scripts/`) — `bash`, `set -euo pipefail`, two-space indent, and a
header comment giving usage, result and the environment variables it reads.

**Markdown** — wrap prose at about 80 columns.

## Commit messages

Subject line: one line, no trailing period, short enough to read in
`git log --oneline`, usually `Area: what changed` where an area is involved:

```
Persist the guest agent token when migrating older VM configs
App: keep the auto-fit window on screen, drive guest resolution through the tools
MCP: start_vm waits for guest tools; record the Claude Code end-to-end run
```

Body: blank line, then prose wrapped at about 80 columns explaining **why** —
what was broken, what the change does about it, and anything a reader would
otherwise have to reconstruct. Bug fixes describe the failure first:

```
Persist the guest agent token when migrating older VM configs

A config written before the agent fields existed got a fresh token and port on
every load, so the process that started the VM and anything connecting to its
guest agent afterwards disagreed and the tools never appeared. loadConfig now
writes the migrated config back. Adds an 'alcovectl agent' probe and the
ALCOVE_OPEN_VM/ALCOVE_AUTOSTART launch hooks used to test the app window.
```

A one-line commit is fine when the subject genuinely says everything. Keep the
`Co-Authored-By:` trailer when an agent wrote the change.

## Before opening a PR

1. `scripts/test/all.sh` passes from a clean checkout of your branch.
2. Run the suites `all.sh` skips that your change touches — the guest agent
   harnesses for `guest-tools/`, `mcp-smoke.py` for `mcp/`, the Windows or
   Ubuntu boot tests for engine and `AlcoveEngine` changes — and say in the PR
   which ones you ran and on which guest.
3. Engine change: patch regenerated, and a fresh `scripts/build-qemu.sh`
   reports the tree as already patched. `QKeyCode.swift` regenerated if
   `qapi/ui.json` moved.
4. Wire-format change: the matching `docs/*-protocol.md` updated in the same
   commit. Design or scope change: a note in `docs/superpowers/specs/` or
   `docs/superpowers/plans/`.
5. New public Swift API has doc comments; new behaviour has a test next to it.
6. Nothing generated or downloaded is staged (`build/`, `images/`,
   `Alcove.xcodeproj/`, `mcp/dist/`, `mcp/node_modules/`). `git status` should
   be quiet after a full test run.
7. Fill in the PR template, including what you could not test — "no Windows
   ISO here" is a useful sentence, a silent gap is not.
