## 1. The `virt` machine (hw/arm/virt.c, docs/system/arm/virt.rst)

### 1.1 Machine type names / aliases

- Versioned types are generated by `DEFINE_VIRT_MACHINE_IMPL(latest, major, minor)`; the `latest` one gets `mc->alias = "virt"` (hw/arm/virt.c:117-148, alias at :127-129).
- In 11.1.1 the latest is `virt-11.1`:
  ```c
  static void virt_machine_11_1_options(MachineClass *mc)
  {
  }
  DEFINE_VIRT_MACHINE_AS_LATEST(11, 1)
  ```
  (hw/arm/virt.c:4444-4447). So `-M virt` == `-M virt-11.1`. Older versioned types exist from `virt-11.0` back to `virt-5.0` (hw/arm/virt.c:4449-4622).
- `virt-11.0` and older set `vmc->hvf_no_kernel_irqchip_default = true` (hw/arm/virt.c:4449-4457); the class field is documented as "HVF specific: support for kernel-irqchip=on introduced in QEMU 11.1" (include/hw/arm/virt.h:158-159). Consequence: on `virt` (= 11.1) **HVF defaults to kernel-irqchip=on**; on `virt-11.0` and older it defaults to off (hw/arm/virt.c:4110-4118, accel/hvf/hvf-all.c:208-213).
- `mc->desc = "QEMU <ver> ARM Virtual Machine"` (hw/arm/virt.c:125).
- Defaults set in class init: `mc->max_cpus = 512`, `mc->block_default_type = IF_VIRTIO`, `mc->no_cdrom = 1`, `mc->default_nic = "virtio-net-pci"`, `mc->default_ram_id = "mach-virt.ram"` (hw/arm/virt.c:4166-4210).

### 1.2 `-cpu` with HVF

- Default CPU type when not TCG is `max`:
  ```c
  static const char *virt_get_default_cpu_type(const MachineState *ms)
  {
      return tcg_enabled() ? ARM_CPU_TYPE_NAME("cortex-a15")
                           : ARM_CPU_TYPE_NAME("max");
  }
  ```
  (hw/arm/virt.c:4120-4124).
- `host` is only in the valid list when `kvm_enabled() || hvf_enabled() || whpx_enabled()` (hw/arm/virt.c:4147-4152). docs: "``host`` (with KVM and HVF only)" and "``max`` (same as ``host`` for KVM and HVF...)" (docs/system/arm/virt.rst:77,81).
- `max` under any hardware accel calls `aarch64_host_initfn()` — comment "When hardware acceleration enabled, '-cpu max' is identical to '-cpu host'" (target/arm/cpu-max.c:196-204).
- `aarch64_host_initfn()` on HVF builds calls `hvf_arm_set_cpu_features_from_host(cpu)` (target/arm/cpu64.c:794-813); the `host` CPU is registered only `#if defined(CONFIG_KVM) || defined(CONFIG_HVF) || defined(CONFIG_WHPX)` (target/arm/cpu64.c:822-826).
- Error if host features cannot be probed: `"The 'host' CPU type can only be used with KVM, HVF or WHPX"` / `"Failed to retrieve host CPU features"` (target/arm/cpu.c:1831-1837).
- HVF host feature set always includes `ARM_FEATURE_PMU` and `ARM_FEATURE_GENERIC_TIMER`, plus `ARM_FEATURE_EL2` if nested virt enabled; MIDR is hard-coded to implementer 0x61 (Apple) (target/arm/hvf/hvf.c:1160-1168, 1198-1206). `pmu` boolean property is added whenever `ARM_FEATURE_PMU` is set (target/arm/cpu.c:1603-1606).

### 1.3 GIC version, MSI controller, ITS with HVF

- Property `gic-version`: "Valid values are 2, 3, 4, x-5, host and max" (hw/arm/virt.c:4279-4283; setter at :3639-3655).
- Which GICs HVF supports (hw/arm/virt.c:2717-2724):
  ```c
  } else if (hvf_enabled()) {
      if (!hvf_irqchip_in_kernel()) {
          gics_supported |= VIRT_GIC_VERSION_2_MASK;
      }
      /* Hypervisor.framework doesn't expose EL2<->1 transition notifiers */
      if (!(!hvf_irqchip_in_kernel() && vms->virt)) {
          gics_supported |= VIRT_GIC_VERSION_3_MASK;
      }
  }
  ```
  - kernel-irqchip=on (default on `virt`/11.1): **only GICv3**.
  - kernel-irqchip=off: GICv2 and GICv3 (GICv3 not allowed if `virtualization=on`).
  - **GICv4 is never offered on HVF** (the v4 mask is only set in the TCG branch, hw/arm/virt.c:2726-2732). `gic-version=4` → `"%s does not support GICv4 emulation, is virtualization=on?"` (hw/arm/virt.c:2662-2667).
  - GICv5: "HVF doesn't have GICv5 support" (hw/arm/virt.c:2734-2737).
- `gic-version=host` → `"gic-version=host requires KVM"` and exit (hw/arm/virt.c:2601-2605).
- `gic-version=max` → v4 if supported else v3 else v2 (hw/arm/virt.c:2610-2623) ⇒ **on HVF, `max` = GICv3**.
- No `gic-version` given (`VIRT_GIC_VERSION_NOSEL`): GICv2 if supported **and** `max_cpus <= GIC_NCPU` (8), otherwise GICv3 (hw/arm/virt.c:2624-2640). So with kernel-irqchip=off and ≤8 vCPUs the default is GICv2; with kernel-irqchip=on it is GICv3.
- With kernel-irqchip=on, HVF instantiates the platform vGIC at distributor 0x08000000 / redistributor 0x080A0000 via `hv_gic_create()`; requires macOS 15.0 else `"HVF: Unsupported OS for platform vGIC."` (target/arm/hvf/hvf.c:1349-1370). These addresses match `VIRT_GIC_DIST`/`VIRT_GIC_REDIST` (hw/arm/virt.c:180, 189).
- MSI controller (`msi=` auto|gicv2m|its|off, hw/arm/virt.c:3430-3447; `its=` is the deprecated bool, :3466-3475, docs/system/arm/virt.rst:191-206):
  - auto + HVF kernel-irqchip → **GICv2m** (hw/arm/virt.c:2771-2772); auto + GICv3 emulated → ITS (:2777).
  - `its=on`/`msi=its` with HVF in-kernel vGIC → `"ITS not supported on HVF when using the hardware vGIC."` and exit (hw/arm/virt.c:2799-2802).
  - GICv2 + ITS → `"GICv2 + ITS is an invalid configuration."` (hw/arm/virt.c:2782-2790).
- `-accel hvf,kernel-irqchip=on|off`; `split` → `"HVF: split irqchip is not supported on HVF."` (accel/hvf/hvf-all.c:233-270, property registered :280-284).

### 1.4 highmem, memory layout, RAM limits, IPA size

- `highmem` default on; `highmem-ecam`, `highmem-mmio`, `highmem-redists` default on; `compact-highmem` on unless class says otherwise (hw/arm/virt.c:4366-4376). docs: docs/system/arm/virt.rst:123-153.
- `highmem=off` forces `pa_bits = 32` (hw/arm/virt.c:2551-2554).
- Memory map: flash at 0x0 size 0x08000000; RAM starts at 1 GiB (`[VIRT_MEM] = { GiB, LEGACY_RAMLIMIT_BYTES }`, hw/arm/virt.c:224) with `LEGACY_RAMLIMIT_GB 255` (:157-158). docs: "Flash memory starts at address 0x0000_0000 / RAM starts at 0x4000_0000" (docs/system/arm/virt.rst:369-371); "large amounts of RAM (at least 255GB, and more if using highmem)" (:51).
- `virt_set_memmap()` errors: `"Addressing limited to %d bits, but memory exceeds it by %llu bytes"`, `"maxmem/slots too huge"` (hw/arm/virt.c:2569-2576).
- With HVF the memmap is computed early via `mc->get_physical_address_range = virt_get_physical_address_range` (hw/arm/virt.c:4081-4104, registered :4189) called from `hvf_accel_init()` with `hvf_arch_get_default_ipa_bit_size()`/`hvf_arch_get_max_ipa_bit_size()` (accel/hvf/hvf-all.c:200-206; target/arm/hvf/hvf.c:1256-1278 using `hv_vm_config_get_default_ipa_size`/`hv_vm_config_get_max_ipa_size`). Too-large `-m`/`maxmem` → `"-m and ,maxmem option values require an IPA range (%d bits) larger than the one supported by the host (%d bits)"` (hw/arm/virt.c:4096-4100).
- `highmem-ecam` is disabled if firmware is loaded and the CPU is not aarch64 (`vms->highmem_ecam &= (!firmware_loaded || aarch64)`, hw/arm/virt.c:3207).

### 1.5 Max CPUs

- `mc->max_cpus = 512` (hw/arm/virt.c:4166-4170). Effective limit: GICv2 → `GIC_NCPU` (8); GICv3 → redistributor capacity of `VIRT_GIC_REDIST` ("allows up to 2*64kB*123 CPUs", hw/arm/virt.c:188-189) plus `VIRT_HIGH_GIC_REDIST2` if `highmem-redists` (hw/arm/virt.c:2969-2980; capacity helper include/hw/arm/virt.h:237-247). Error: `"Number of SMP CPUs requested (%d) exceeds max CPUs supported by machine 'mach-virt' (%d)"` + hint `"Try 'highmem-redists=on' for more CPUs"` (hw/arm/virt.c:2983-2992). docs: "many CPUs (up to 512 if using a GICv3 and highmem)" (docs/system/arm/virt.rst:52).
- No HVF-specific vCPU cap in accel/hvf or target/arm/hvf (grep for `max_cpus`/`hv_vm_get_max_vcpu_count`: NOT FOUND). Each vCPU gets its own thread `"CPU %d/HVF"` and `hv_vcpu_create()` (accel/hvf/hvf-accel-ops.c:122-146, 192-206).

### 1.6 ramfb on virt

- `TYPE_RAMFB_DEVICE` is `"ramfb"` (include/hw/display/ramfb.h:14). virt allows it as a dynamic sysbus device: `machine_class_allow_dynamic_sysbus_dev(mc, TYPE_RAMFB_DEVICE);` (hw/arm/virt.c:4170).
- Built when `CONFIG_FW_CFG_DMA` (hw/display/meson.build:6-8); `ARM_VIRT` does `select FW_CFG_DMA` (hw/arm/Kconfig:18). Realize fails with `"ramfb device requires fw_cfg with DMA"` otherwise (hw/display/ramfb.c:145-148). Properties: `x-migrate` (default true), `use-legacy-x86-rom` (default false) (hw/display/ramfb-standalone.c:66-70).
- `virtio-ramfb`: **NOT FOUND** anywhere under hw/ or include/.
- docs: there is no default display on virt; "The recommended option is ``virtio-gpu-pci``" (docs/system/arm/virt.rst:99-104).

### 1.7 pflash layout, `-drive if=pflash`, `-bios`

- Two `TYPE_PFLASH_CFI01` devices are created in instance_init: child names `virt.flash0` / `virt.flash1`, aliased as machine properties `pflash0` / `pflash1` (drive links) (hw/arm/virt.c:1806-1810, 1781-1804, called at :4400). Parameters: `sector-length` = 256 KiB, `width` 4, `device-width` 2, ids 0x89/0x18 (hw/arm/virt.c:1779, 1791-1797).
- Mapping: the 128 MiB `VIRT_FLASH` region is split in two 64 MiB halves; flash0 at `flashbase`, flash1 at `flashbase + flashsize` (hw/arm/virt.c:1828-1847). DT node `/flash@0` with `compatible = "cfi-flash"`, `bank-width = 4` (hw/arm/virt.c:1849-1863).
- Legacy `-drive if=pflash` mapping:
  ```c
  static bool virt_firmware_init(VirtMachineState *vms,
                                 MemoryRegion *sysmem,
                                 MemoryRegion *secure_sysmem)
  ```
  loops `pflash_cfi01_legacy_drive(vms->flash[i], drive_get(IF_PFLASH, 0, i))` for i=0,1 (hw/arm/virt.c:1893-1905). `pflash_cfi01_legacy_drive()` errors `"clashes with -machine"` if the `pflash0/1` property was also set (hw/block/pflash_cfi01.c:998-1015). `unit=` selection: explicit `unit`, else first free unit in order (blockdev.c:911-935). ⇒ first `-drive if=pflash` is unit 0 (code), second is unit 1 (vars).
- `-bios file` loads into the flash0 MMIO region with `load_image_mr()`; combining with a pflash unit 0 drive → `"The contents of the first flash device may be specified with -bios or with -drive if=pflash... but you cannot use both options at once"`; `firmware_loaded = pflash_blk0 || bios_name` (hw/arm/virt.c:1911-1940). `-bios` option doc: qemu-options.hx:4579-4584. Note `-bios` gives a read-only ROM image with no vars store; for a persistent UEFI variable store use unit 1 pflash.
- Reference command line in-tree (Arm virt):
  ```
  -drive if=pflash,format=raw,file=flash0.img,readonly=on \
  -drive if=pflash,format=raw,file=flash1.img
  ```
  (docs/specs/tpm.rst:378-379).
- Also allowed on virt: `uefi-vars-sysbus` (`TYPE_UEFI_VARS_SYSBUS`, hw/arm/virt.c:4171; include/hw/uefi/var-service-api.h:11; `UEFI_VARS default y if ... AARCH64`, hw/uefi/Kconfig:1-3).
- If firmware is loaded and CPU is aarch64 and ACPI enabled, ACPI tables are built (hw/arm/virt.c:3214).

### 1.8 edk2 firmware blobs: where decompressed and installed

- Shipped compressed: `pc-bios/edk2-aarch64-code.fd.bz2` (1,565,763 bytes) and `pc-bios/edk2-arm-vars.fd.bz2` (263 bytes). There is **no** `edk2-aarch64-vars.fd`; the aarch64 vars template is `edk2-arm-vars.fd` (pc-bios/ listing; pc-bios/descriptors/60-edk2-aarch64.json:12-15).
- Decompression rule (pc-bios/meson.build:2-28):
  ```
  roms += custom_target(f, build_by_default: have_system, output: f,
                input: files('@0@.bz2'.format(f)), capture: true,
                install: get_option('install_blobs'), install_dir: qemu_datadir,
                command: [ bzip2, '-dc', '@INPUT0@' ])
  ```
  So `edk2-aarch64-code.fd` appears in the build dir under `pc-bios/` and is installed to `qemu_datadir` (= `datadir/qemu_suffix`, meson.build:45) when `install_blobs` is on.
- `unpack_edk2_blobs` is true when `aarch64-softmmu` (or another edk2 target) is in `target_dirs` and `bzip2` is found (meson.build:170-178).
- Firmware descriptor `60-edk2-aarch64.json`: executable `@DATADIR@/edk2-aarch64-code.fd` (raw), nvram-template `@DATADIR@/edk2-arm-vars.fd`, targets `aarch64` / `virt-*` (pc-bios/descriptors/60-edk2-aarch64.json:6-24); installed to `qemu_datadir/firmware` (pc-bios/descriptors/meson.build:1-18).

### 1.9 Other machine options that matter with HVF

- `secure=on` requires TCG: `"mach-virt: %s does not support providing Security extensions (TrustZone) to the guest CPU"` (hw/arm/virt.c:2996-3001).
- `virtualization=on` is allowed with HVF (hw/arm/virt.c:3009-3014) and its setter immediately calls `hvf_nested_virt_enable(value)` (hw/arm/virt.c:3288-3298). See §6.
- `mte=on` + HVF → `"mach-virt: %s does not support providing MTE to the guest CPU"` (hw/arm/virt.c:3017-3022).
- PSCI conduit: SMC if `virt`, else HVC (hw/arm/virt.c:2956-2962); HVF implements PSCI 1.1 (target/arm/cpu.c:1292-1295).
- `virtio-mmio-transports` 0..32 (default `NUM_VIRTIO_TRANSPORTS` = 32, include/hw/arm/virt.h:47; docs/system/arm/virt.rst:249-252).

## 3. TPM (swtpm) with `tpm-tis-device`

- swtpm start (does not need root) (docs/specs/tpm.rst:330-339):
  ```
  mkdir /tmp/mytpm1
  swtpm socket --tpmstate dir=/tmp/mytpm1 \
    --ctrl type=unixio,path=/tmp/mytpm1/swtpm-sock \
    --tpm2 \
    --log level=20
  ```
- Arm virt example (docs/specs/tpm.rst:366-379):
  ```
  qemu-system-aarch64 -machine virt,gic-version=3,acpi=off \
    -cpu host -m 4G \
    -nographic -accel kvm \
    -chardev socket,id=chrtpm,path=/tmp/mytpm1/swtpm-sock \
    -tpmdev emulator,id=tpm0,chardev=chrtpm \
    -device tpm-tis-device,tpmdev=tpm0 \
    -device virtio-blk-pci,drive=drv0 \
    -drive format=qcow2,file=hda.qcow2,if=none,id=drv0 \
    -drive if=pflash,format=raw,file=flash0.img,readonly=on \
    -drive if=pflash,format=raw,file=flash1.img
  ```
- Option grammar: `-tpmdev emulator,id=id,chardev=dev` (qemu-options.hx:4473-4474, 4523-4529). The doc text says "(Linux-host only)" for the emulator backend (qemu-options.hx:4523-4524), but the build gate is `TPM_EMULATOR default y depends on TPM_BACKEND` with no Linux dependency (backends/tpm/Kconfig:11-14) and `have_tpm` only excludes Windows (meson.build:222-224) — the doc string is stale relative to Kconfig; runtime on macOS not exercised here.
- `tpm-tis-device` properties: `irq` (default `TPM_TIS_IRQ`), `tpmdev`, `ppi` (default **true**) (hw/tpm/tpm_tis_sysbus.c:94-98). PPI on ARM64 virt: "-device tpm-tis-device,tpmdev=tpm0,ppi=on"; "Without PPI, guest operating systems such as Windows 11 ARM64 will log errors when attempting to query TPM Physical Presence capabilities via the ACPI _DSM method." (docs/specs/tpm.rst:190-210).
- The device is a dynamic sysbus device on the virt platform bus, allowed under `#ifdef CONFIG_TPM` (hw/arm/virt.c:4174-4176); TPM2 ACPI table generation lives in hw/arm/virt-acpi-build.c (docs/specs/tpm.rst:212-214).

## 4. User networking (slirp) and vmnet

### 4.1 `-netdev user`

- Defaults ("historic slirp"): network 10.0.2.0/24, host 10.0.2.2, DHCP start 10.0.2.15, DNS 10.0.2.3 (net/slirp.c:446-450). docs: `net=` default 10.0.2.0/24, `host=` default x.x.x.2, `dns=` default x.x.x.3 (qemu-options.hx:3366-3372, 3400-3403). (The prompt's "DNS 10.0.3" is 10.0.2.**3**.)
- `hostfwd=[tcp|udp|unix]:[[hostaddr]:hostport|hostpath]-[guestaddr]:guestport` (qemu-options.hx:3484-3520). Implementation `static int slirp_hostfwd(SlirpState *s, const char *redir_str, Error **errp)` (net/slirp.c:803-956). `unix:` host side requires `!WIN32 && SLIRP_CHECK_VERSION(4, 7, 0)`; path must be absolute and, if it exists, must be a socket and is unlinked first (net/slirp.c:806-808, 838-885). Errors: `"Invalid host forwarding rule '%s' (%s)"` / `"Could not set up host forwarding rule '%s'"` (net/slirp.c:943-955). Example: `-nic user,hostfwd=unix:/tmp/vm-:23` (qemu-options.hx:3520).
- `guestfwd=[tcp]:server:port-dev` or `...-cmd:command` (qemu-options.hx:3522-3545). Implementation `static int slirp_guestfwd(SlirpState *s, const char *config_str, Error **errp)` (net/slirp.c:1118-1197): TCP only (`/* TODO: IPv6 */`, :1120), the `dev` part is passed to `qemu_chr_new_mux_mon(buf, p, NULL)` (:1161). **Yes, a host unix socket can be exposed**: a chardev spec of the form `unix:/path` is parsed to `backend=socket,path=/path` (chardev/char.c:521-527); via this legacy path `server` defaults to **false** (`sock->server = qemu_opt_get_bool(opts, "server", false)`, chardev/char-socket.c:1473-1474), i.e. QEMU **connects as a client** to an existing host unix socket. So `-netdev user,id=n0,guestfwd=tcp:10.0.2.100:1234-unix:/path/to/host.sock` makes guest TCP connections to 10.0.2.100:1234 flow to that host unix socket (the `server` address must be inside the guest network per the doc example at qemu-options.hx:3533-3535). Alternative `cmd:` spawns a program per connection via `slirp_add_exec` (net/slirp.c:1151-1157).

### 4.2 vmnet backends (macOS)

- Sources: `net/vmnet-common.m`, `net/vmnet-shared.c`, `net/vmnet-bridged.m`, `net/vmnet-host.c`, `net/vmnet_int.h`. Built only if the vmnet framework is found **and** `VMNET_BRIDGED_MODE` exists in `vmnet/vmnet.h` (`CONFIG_VMNET`), else "vmnet.framework API is outdated" (meson.build:1227-1237, 2513).
- Option grammar (qemu-options.hx:3128-3145):
  ```
  -netdev vmnet-host,id=str[,isolated=on|off][,net-uuid=uuid]
           [,start-address=addr,end-address=addr,subnet-mask=mask]
  -netdev vmnet-shared,id=str[,isolated=on|off][,nat66-prefix=addr]
           [,start-address=addr,end-address=addr,subnet-mask=mask]
  -netdev vmnet-bridged,id=str,ifname=name[,isolated=on|off]
  ```
  QAPI: `NetdevVmnetHostOptions` (qapi/net.json:728-768), `NetdevVmnetSharedOptions` (:771-814), `NetdevVmnetBridgedOptions` (:816-835); all `'if': 'CONFIG_VMNET'`. `isolated` and `net-uuid` "Requires at least macOS Big Sur 11.0" (qapi/net.json:748-757, 795-798). `start-address`/`end-address`/`subnet-mask` must be given together (net/vmnet-shared.c:20-38; net/vmnet-host.c:32-42).
- `vmnet-bridged` validates `ifname` against `vmnet_copy_shared_interface_list()` and errors `"unsupported ifname '%s', expected one of [ %s]"` (net/vmnet-bridged.m:20-37, 69-92).
- Interface creation: `int vmnet_if_create(NetClientState *nc, xpc_object_t if_desc, Error **errp)` uses `vmnet_start_interface()`; failure → `"cannot create vmnet interface: %s"` (net/vmnet-common.m:290-368). Status strings include `VMNET_FAILURE` → `"general failure (possibly not enough privileges)"` and `VMNET_INVALID_ACCESS` → `"invalid access, permission denied"` (net/vmnet-common.m:30-56).
- Root / `com.apple.vm.networking` entitlement: **NOT FOUND** — no source comment, error string, QAPI doc, or docs/ text in the tree mentions root, sudo, or `com.apple.vm.networking` for vmnet (grep over net/vmnet-*, qapi/net.json, qemu-options.hx, docs/). The only in-tree hint is the "possibly not enough privileges" status string above. Any statement about which modes need root vs. entitlement must come from Apple's vmnet documentation, not this tree.

## 5. Disk images on macOS

- `qemu-img create [-f FMT] [-o FMT_OPTS] [-b BACKING_FILE [-B BACKING_FMT]] [-u] [-q] [--object OBJDEF] FILE [SIZE]` (docs/tools/qemu-img.rst:474-497). qcow2 `-o` options include `compat` (0.10/1.1), `backing_file`, `compression_type`, `encryption`, `cluster_size`, `preallocation` (docs/tools/qemu-img.rst:798-866).
- Internal snapshots: `qemu-img snapshot [-l | -a SNAPSHOT | -c SNAPSHOT | -d SNAPSHOT] FILENAME` (docs/tools/qemu-img.rst:674-676; flags :241-259). VM snapshots (`savevm`/`loadvm`) require "at least one non removable and writable block device using the ``qcow2`` disk image format" (docs/system/images.rst:41-45).
- `-drive` `cache=` modes table (`writeback` default; `none` = `cache.direct=on`) (qemu-options.hx:1755-1774). `aio=` is "threads", "native", or "io_uring" (qemu-options.hx:1776-1778), but on macOS:
  - `O_DIRECT` does not exist on macOS; file-posix defines `#ifndef O_DIRECT / #define O_DIRECT O_DSYNC` (block/file-posix.c:121-124) and `cache.direct`/`BDRV_O_NOCACHE` just ORs that flag in (block/file-posix.c:549-553). So `cache=none` on macOS means `O_DSYNC`, not true direct I/O. No `F_NOCACHE` usage in file-posix.c (grep: NOT FOUND).
  - `aio=native` requires `CONFIG_LINUX_AIO`, otherwise `"aio=native was specified, but is not supported in this build."`; `aio=io_uring` requires `CONFIG_LINUX_IO_URING`, otherwise `"aio=io_uring was specified, but is not supported in this build"` (block/file-posix.c:731-766). Default is `BLOCKDEV_AIO_OPTIONS_THREADS` (block/file-posix.c:637-644). ⇒ **`aio=threads` only on macOS.**
  - Discard/unmap: `discard=ignore|unmap` and `detect-zeroes=off|on|unmap` (qemu-options.hx:1544-1555, 1707). On macOS regular-file discard is implemented with `fcntl(s->fd, F_PUNCHHOLE, &fpunchhole)`; `ENODEV` → `-ENOTSUP` and `has_discard` is cleared (block/file-posix.c:2311-2328). `pdiscard_alignment` is taken from `fstatfs()` `f_bsize` on Apple (block/file-posix.c:1548-1555).
  - Device geometry on macOS uses `DKIOCGETBLOCKCOUNT`/`DKIOCGETBLOCKSIZE` (block/file-posix.c:2880-2887); optical-media host device code is `#if defined(__APPLE__) && defined(__MACH__)` (block/file-posix.c:4005-4118).
- Guest-side `discard` for `virtio-blk-pci`/`nvme` is a device property matter (not re-verified here); the host-side path above is what makes `discard=unmap` effective on APFS.

## 6. HVF specifics (target/arm/hvf/hvf.c, accel/hvf/*)

- Nested virtualization (EL2) **is supported in 11.1.1**: `hv_vm_config_get_el2_supported()` / `hv_vm_config_set_el2_enabled(config, true)` guarded by `__builtin_available(macOS 15.0, *)`:
  ```c
  static bool hvf_arm_el2_supported(void)
  hv_return_t hvf_arch_vm_create(MachineState *ms, uint32_t pa_range)
  ```
  (target/arm/hvf/hvf.c:1310-1320, 1323-1375). Enabled via `-M virt,virtualization=on` → `hvf_nested_virt_enable()` (hw/arm/virt.c:3288-3298; accel/hvf/hvf-all.c:30-33; include/system/hvf.h:31-39). Errors: `"Nested virtualization not supported on this system."`, `"Failed to enable nested virtualization."` (target/arm/hvf/hvf.c:1337-1345). With nested virt, `ARM_FEATURE_EL2` is set and SME is masked (`FIELD_DP64_IDREG(&host_isar, ID_AA64PFR1, SME, 0)`) (target/arm/hvf/hvf.c:1167-1169, 1227-1230); PSCI target EL becomes 2 (target/arm/hvf/hvf.c:1546-1551). Note the GIC restriction: with `virtualization=on` and kernel-irqchip=off only GICv2 is offered (§1.3).
- macOS version checks: `__builtin_available(macOS 15.0, *)` for EL2 and the in-kernel vGIC (target/arm/hvf/hvf.c:1313, 1334, 1350); `__builtin_available(macOS 15.2, *)` for SME2 feature registers (:1175, 1391); `#if !defined(MAC_OS_VERSION_26_0)` workaround for `HV_SYS_REG_MDCR_EL2` in older SDKs (:474-481). vmnet `isolated`/`net-uuid` need macOS 11 (qapi/net.json:748-757).
- IPA size: `hv_vm_config_set_ipa_size(config, pa_range)` with `pa_range` from `virt_get_physical_address_range()` (target/arm/hvf/hvf.c:1326-1331; hw/arm/virt.c:4081-4104).
- SMP > 1: one HVF thread per vCPU, each calling `hv_vcpu_create()`; no vCPU cap in HVF code (accel/hvf/hvf-accel-ops.c:122-146, 192-206). Limits come from the virt GIC rules in §1.5.
- PMU with `-cpu host`: `ARM_FEATURE_PMU` is always advertised (target/arm/hvf/hvf.c:1164). With kernel-irqchip=off QEMU emulates a cycles counter (PMUVer=0) which is "enough to make Windows happy"; with kernel-irqchip=on `ID_AA64DFR0_EL1.PMUVer` is set to 1 and "the OS provides its own PMU emulation, which is currently a cycles counter only emulation" (target/arm/hvf/hvf.c:1208-1225; emulation in :1695-1705, 1882-1996).
- Missing hypervisor entitlement: `hv_vm_create()` returning `HV_DENIED` yields
  `"Could not access HVF. Is the executable signed with com.apple.security.hypervisor entitlement?"` then `exit(1)`; any other failure aborts via `assert_hvf_ok` with `"Error: %s = %s (0x%x, at %s:%u)"` (accel/hvf/hvf-all.c:215-221, 50-61). The build signs the binary with `accel/hvf/entitlements.plist` (`com.apple.security.hypervisor` = true) using `codesign --entitlements ... --force -s -` via `scripts/entitlement.sh` on darwin when `CONFIG_HVF` is in the target (accel/hvf/entitlements.plist:4-7; scripts/entitlement.sh:24-26; meson.build:4459-4480). If you re-sign or copy the binary without that entitlement, the HV_DENIED message above is what you get.
- HVF is enabled at configure only if the Hypervisor framework is found (`CONFIG_HVF`), else `"HVF not available on this platform"` when `-Dhvf=enabled` (meson.build:903-910, 955-957).

## 7. Command-line skeleton derived from the above (each element traceable to a citation in §1-6)

```
qemu-system-aarch64 \
  -M virt \                                  # = virt-11.1; HVF kernel-irqchip=on by default (§1.1)
  -accel hvf \                               # add ,kernel-irqchip=off for GICv2/ITS-capable emulated GIC (§1.3)
  -cpu host -smp 4 -m 8G \                   # 'max' would be identical under HVF (§1.2)
  -drive if=pflash,format=raw,readonly=on,file=<datadir>/edk2-aarch64-code.fd \   # unit 0 (§1.7/1.8)
  -drive if=pflash,format=raw,file=vars.fd \                                       # unit 1, copy of edk2-arm-vars.fd
  -device ramfb \                            # or -device virtio-gpu-pci (§1.6, §2)
  -device qemu-xhci -device usb-kbd -device usb-tablet \
  -drive if=none,id=d0,file=disk.qcow2,format=qcow2,discard=unmap,aio=threads \   # aio=threads only on macOS (§5)
  -device virtio-blk-pci,drive=d0 \          # or -device nvme,drive=d0,serial=...
  -netdev user,id=n0,hostfwd=tcp::2222-:22 -device virtio-net-pci,netdev=n0 \
  -chardev socket,id=chrtpm,path=/tmp/mytpm1/swtpm-sock \
  -tpmdev emulator,id=tpm0,chardev=chrtpm -device tpm-tis-device,tpmdev=tpm0 \   # ppi=on default (§3)
  -audiodev coreaudio,id=a0 -device virtio-sound-pci,audiodev=a0                   # or intel-hda + hda-duplex (§2)
```
Note: with the default in-kernel vGIC, MSIs come from GICv2m, not ITS (§1.3).
