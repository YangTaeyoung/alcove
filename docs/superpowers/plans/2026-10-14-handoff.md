## Goal and the user's instructions

- Build every testing aid from the spec so a coding agent can deploy a Windows `.exe` (an AI chatbot app) into an

- Work autonomously: plan → implement → run on the real VM → verify; report only at the end.
- When everything is done: bump the minor version (0.1.0 → 0.2.0), merge, publish a GitHub Release, then report.

## Setting up the other Mac

1. Clone: `git clone git@github.com:YangTaeyoung/alcove.git`; the work is on `main`.
2. Toolchain: Go 1.25, Swift 6.3.3 (the Xcode of the `macos-26` CI image, which CI builds and tests with), Node 26,
   Python 3, `xcodegen`.
3. Engine: `scripts/build-qemu.sh` (QEMU 11.1.1 + `qemu-patches/0001–0003`, configured with `--disable-pvg`) →
   `build/qemu-build`. Tests that start the engine read `ALCOVE_QEMU_DIR=<repo>/build/qemu-build`.
4. Guest builds: `scripts/test/all.sh` (agent, fixture `build/alcove-fixture-windows-arm64.exe`, `alcove-proxy`).
5. The test VM: copy `~/Library/Application Support/Alcove/` (the `Windows 11.alcovevm` bundle, ~32 GiB, plus
   `test_id_ed25519`) to the same path. The Windows 11 ARM64 image cannot be re-downloaded by script. Guest user
   alcove/alcove (administrator); agent host port 17532; ssh on 127.0.0.1:2222 with that key (use
   `-o UserKnownHostsFile=/dev/null -o StrictHostKeyChecking=no`; never edit `~/.ssh`). Exclude the `VMs` folder from
   Time Machine (local snapshots keep the old blocks of the disk image).
6. HTTP capture CA: `~/Library/Application Support/Alcove/proxy-ca/` is created on first use; nothing to copy.
7. Control server for e2e runs: `cd AlcoveKit && swift build --product alcovectl --scratch-path .build-ctl`, then
   `.build-ctl/debug/alcovectl serve`; `python3 scripts/test/ctl.py <op> key=value…`. Install the branch's agent in the
   guest with `scripts/test/install-agent.py` when its build differs.
8. Before resuming: build and run the full suite once (`cd AlcoveKit && swift build --build-tests && swift test
   --skip-build`), `cd mcp && npm ci && npm run build && npm test`, `cd guest-tools && go test ./...`, then
   `python3 scripts/test/at1-e2e.py` against the VM.

## Operating rules that held up

- One agent at a time drives the VM and the main checkout; other implementers work in isolated worktrees and their
  commits are cherry-picked in.
- Free disk ≥ 10 GiB for any VM run, ≥ 18 GiB before a running-VM snapshot (it writes the guest memory into the qcow2).
- After every e2e: the VM stopped through `vm.stop`, the guest as found, no control server or proxy left running.
- Comments and test names say only what code does now; error strings are sentences that name the next step.
