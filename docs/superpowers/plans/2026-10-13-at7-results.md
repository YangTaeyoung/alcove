# AT7 results: HTTP capture and fault injection (2026-10-14)

The runs below were executed on an Apple M5 Pro (18 cores, 64 GiB RAM,
macOS 27.0.1, Swift 6.4, Go 1.25.0, Node 26, Python 3, QEMU 11.1.1 with
`qemu-patches/0001` to `0003`) against the VM `Windows 11` (Windows 11 Pro
ARM64 25H2, build 26200, Windows PowerShell 5.1.26100, user `alcove`, 4 vCPUs,
6 GiB, 1280x800, guest agent 0.2.0 installed as the scheduled task
`AlcoveAgent`, elevated, equal to `build/alcove-agent-windows-arm64.exe`)
through `alcovectl serve` (debug build of this tree in `AlcoveKit/.build-ctl`)
and `build/alcove-proxy` built from this tree. The data volume had 498 GiB to
510 GiB free. They are reproducible with the scripts named.

## Final output

`python3 scripts/test/at7-e2e.py`, the first of the two final runs:


The second run differs in its numbers only: proxy port 50305, 92 ms, 3035 ms,
first event 1.64 s before the last, MCP exchange 5. The five events were sent
1.6 s apart in all, so the guest saw them as they were sent.

Exchange 18 being the fixture's request in check 2 shows the background
traffic that the system proxy also captures: Windows' connectivity probe
(`www.msftconnecttest.com`, and `ipv6.msftconnecttest.com`, which the proxy
answers with 502 because the Mac has no IPv6 route), SmartScreen and
telemetry. The checks filter by host and by the exchange id before the action.

## Guest trial of the control side

Before the end-to-end script, the recipes and ops of Task 2 were run in the
guest one by one (lists of `task-2-fix2-report.md`, `task-2-fix2-rereview.md`,
`task-2-fix3-rereview.md`, `task-2-fix3-report.md`). The recipes rendered by
the product equal the texts reviewed in Task 2. No product defect was found;
the full table is in the task report of the working ledger. In short:

- **WinHTTP blob.** For `netsh winhttp set proxy proxy-server=10.0.2.2:<port>
  bypass-list=<local>` with ports 49152, 5, 8080, 9999 and 12345 the value is
  `28 00 00 00 | 00 00 00 00 | 03 00 00 00 | <length> 00 00 00 | "10.0.2.2:<port>"
  | 07 00 00 00 | "<local>"` (length `0x0E`, `0x0A`, `0x0D`, `0x0D`, `0x0E`),
  and `readSystemProxy` reads each port. A corporate WinHTTP proxy came back
  byte for byte after a capture.
- **Every Windows recipe** in PowerShell 5.1: exit 0, one JSON line, empty
  stderr; a second set takes the `Replace` path (`keptPrevious: true`), a
  record over an unclean capture restores; a set with another thumbprint
  removes the recorded certificate from `Root`.
- **State file reads.** A lock of 300 ms is outlasted by the three reads
  (state read after 490 ms), a lock of 1 s gives `previousUnreadable` (after
  664 ms), a file deleted while locked reads as missing. An empty, half or
  version 2 file: `previousUnreadable: true`, `clear` and `set` exit 2 with
  the sentence, the file unchanged; `vm.http.start` answers the sentence
  verbatim, adds no certificate to `Root` and keeps the journal entry; the
  boot cleanup then fails and writes the line to stderr and the system log;
  after the file was deleted, `vm.http.stop` cleared the entry.
- **Sequences.** No proxy; `corp:8080` with an `ExpandString` override and a
  `String` `ProxyEnable`; a PAC URL; a user's `10.0.2.2:8888` (doctor text,
  stop without a capture, `systemProxy: false`, full capture); `110.0.2.2:3128`
  (not taken for Alcove's); a restore cut before `ProxyServer` and stopped
  again; a `ProxyServer` changed during the capture (kept); a state file
  deleted during the capture (the dead proxy stays, as documented); a leftover
  `.new` file (deleted). Every recorded value came back. WinINET stores
  `ProxyEnable` as REG_DWORD and `ProxyOverride` as REG_SZ whenever it rereads
  its settings (`InternetSetOption` 39 and 37 on values set by hand change the
  kinds the same way), and it advances the change counter of
  `DefaultConnectionSettings`.
- **Journal recovery.** `kill -9` of `alcovectl serve` during a capture: the
  proxy exited with it; the next server stopped the orphaned engine on
  `vm.start`, the tools connected after 21.8 s and the entry was gone and the
  guest restored 26.8 s after `vm.start`. `vm.stop` of a paused capturing VM
  warned `(the VM was paused)`; the next boot cleaned the guest 3 s after the
  tools connected. This is the check the brief's end-to-end script would have
  added; the script does not repeat it.
- **Snapshots.** A snapshot taken during a capture is noted;
  `vm.snapshot.restore` of it after a clean stop answered
  `staleProxyCleared: true`, and during a live capture also `captureEnded:
  true`, with no `alcove-proxy` left; deleting the snapshot removed the note.
  The control server held a new agent connection after each restore.
- **Programs.** See the table in `docs/control-protocol.md` ("Which programs
  are captured"): Go via `HTTPS_PROXY`, `Invoke-WebRequest`,
  `WinHttp.WinHttpRequest.5.1` and an Edge that ran before the capture all
  went through the proxy and trusted the CA; `curl.exe` needs `-x` or
  `HTTPS_PROXY` and `--ssl-no-revoke` (`CRYPT_E_NO_REVOCATION_CHECK`
  otherwise). Requests to a plain server on the Mac at `10.0.2.2:<port>` are
  captured; one to a Mac server with a self-signed certificate answers 502
  naming the unknown authority.
- **Without elevation** (`runas /trustlevel:0x20000`, Administrators removed
  from the token): `set` and `remove` exit 2 with sentences that name
  elevation; `read` and `clear` see no state file and report nothing to do
  (`C:\ProgramData\Alcove` admits Administrators and SYSTEM only).
- **Journal files**: folder 0700, `captures.json` and its lock 0600.

Not run: the app's window paths (boot, restore, Suspend All, Reset, snapshot
sheet), two hosts with equally named VMs, a symbolic link in `--dir`, every
Linux item, Node, Python, Java and Firefox in the guest.
