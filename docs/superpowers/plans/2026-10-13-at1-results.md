## Defects found and fixed

Found while verifying the agent in the VM (Task 7a):

| Defect | Cause | Fix | Commit |
|---|---|---|---|
| `shell: "cmd"` broke commands that start with a quoted path (`The directory name is invalid.`) | The raw line was `cmd.exe /C <cmd>`; without `/S`, `cmd.exe` strips the first and the last quote of such a line | The line is `cmd.exe /S /C "<cmd>"` | `014acf7` |
| `fs.list` with `sha256` failed as a whole on a file another process held open | The walk stopped at the first digest error | Such a file is listed without `sha256` | `1c244e6` |
| A GUI program started with `shell: "none"` had a hidden main window | `SW_HIDE` was set in addition to `CREATE_NO_WINDOW` | Children start with `CREATE_NO_WINDOW` only | `6d96f02` |
| Non-ASCII `stdin` reached PowerShell garbled | `[Console]::InputEncoding` was the OEM code page | The PowerShell prefix sets `[Console]::InputEncoding` to UTF-8 | `6012fa6` |
| A PowerShell command that read stdin without a `stdin` parameter blocked until the timeout; the v1 `exec` blocked its connection | Go connected the child to `NUL`, on which .NET's console input stream does not return | `exec.run` and v1 `exec` always give the child a pipe, at end-of-file when there is no text | `bba7567` |

Found by the end-to-end run through the control socket (Task 7b):

| Defect | Cause | Fix | Commit |
|---|---|---|---|
| `vm.fs.read` with `tail`, or from an offset, returned NUL and U+FFFD characters for files Windows PowerShell wrote with `>` or `Out-File` | Those files are UTF-16LE. `fs.tail` split lines at the byte `0A`, which left the piece one byte out of step, and the host recognised UTF-16 only by a byte order mark at the start of the bytes it had been given | `fs.read` and `fs.tail` report `encoding: "utf-16le"` for a file that begins with `FF FE`; `fs.tail` works in 2-byte code units for such a file; `vm.fs.read` decodes by the reported encoding | `6981157`, `44294ff` |
| `vm.exec` answered `guest tools in 'Windows 11' disconnected during vm.exec` when both output streams were full of characters that JSON escapes (200000 NUL or `<` characters each); `vm.exec.read` likewise | The agent's reply was 2.4 MB after escaping and the host transport dropped the connection at 2 MiB | The host reads lines up to 8 MiB | `e779fb4` |
| `vm.exec` with more than 1 MiB of `stdin` (or `command`, or `vm.exec.write` data) answered the same `disconnected` error, on every retry | The agent reads lines up to 1 MiB and closed the connection on a longer one | The host answers such a request with `request '<op>' is longer than 1 MiB, the most alcove-agent reads in one message; put large input in a guest file and pass its path` and does not send it | `e779fb4` |

## What differed from the plan

- The control-socket client is `Client.call(op, reply_timeout=…, **params)`,
  not `call(op, timeout=…, **params)`: `timeout` is a parameter of `vm.exec`
  and `vm.wait_idle`, so every keyword except `reply_timeout` goes to the
  server. `Client.arrival(id)` reports the position and time of a reply, which
  the ordering check needs.
- The stdio JSON-RPC helper moved from `mcp-smoke.py` to
  `scripts/test/mcp_stdio.py`; it reads the server on a thread so its timeout
  holds, and raises `MCPError` instead of exiting.
- `install-agent.py` and `agent-rpc-windows.py` were written in Task 7a; this
  task changed `install-agent.py` only to use the shared client.
- `at1-e2e.py` has nine checks instead of eight (refusals), and its checks
  cover more than the plan listed: `vm.exec.write`, `vm.exec.list`,
  `vm.process.kill`, `shell: cmd`, `argv`, every MCP tool of the `shell` and
  `files` toolsets, large replies and oversized requests.
- The agent contract gained one result field: `encoding` in `fs.read` and
  `fs.tail`.
- `scripts/test/all.sh` gained `npm run build && npm test` for `mcp/` (with
  `npm ci` when `node_modules` is missing) and `mcp-smoke.py --list-only`.
- The path through an agent without the request/response layer (v1 fallback of
  `vm.exec`, `too old` errors) could not be run in the VM, which has the new
  agent; it is covered by `testExecFallsBackToV1` and
  `testOldAgentErrorNamesTheUpdate` only.

## Open

- PowerShell's `$input` does not decode non-ASCII stdin (`가` arrives as
  `Ω░Ç`); `[Console]::In` does. Documented in `docs/agent-protocol.md`.
- With `shell: "cmd"`, non-ASCII output of `cmd.exe` built-ins is lossy
  (`echo 한글` → `??`, also after `chcp 65001` in the same line). Running `cmd
  /c` from the default PowerShell shell prints UTF-8. Documented.
- `vm.fs.read` cuts ranges by bytes; a character that straddles two ranges
  reads as U+FFFD in both. Documented.
- A command that `vm.exec` started keeps running in the guest after its
  connection closes, until it ends or times out. Documented.
- Errors of the agent pass through the control socket and MCP unchanged, so
  they name agent operations (`call exec.list`) where the caller knows
  `vm.exec.list` or `alcove_exec_list`. Some name the path but no next step
  (`'<path>' does not exist`).
- `exec.list` returns the whole command text of up to 64 jobs; with very long
  commands that reply can pass the host's 8 MiB line limit.
- A control request line over 8 MiB closes the connection without a reply.
- `AgentVersion` is still `0.2.0` although the agent changed several times;
  `install-agent.py` tells builds apart by SHA-256, the handshake cannot.
- Not exercised: Linux guests through the new operations, the Alcove app as
  the owner of the control socket (the run used `alcovectl serve`), the
  `starting` / `paused` branches of `install-agent.py`.
